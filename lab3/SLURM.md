# Лаба 3: запуск в проверенном окружении Slurm

Проверено пользователем 11.11.2026: очередь `batch`, модули `intel/icc18`
(Intel C++ 18.0.2), `intel/mpi5` (MPI 5.1.3), Python 3.6.8 без NumPy.
Старые `job.pbs`, `run_cluster.sh`, `korolev_mpirun.sh` относятся к TORQUE
из опубликованных инструкций и **не применяются к текущему окружению**.

Проба 345024 остановилась при компиляции на вычислительном узле: Intel сообщил
`#10417`, не найдя настройки C++-заголовков из GCC. Синтаксическая проверка того же
исходника на узле входа прошла. Поэтому сборка вынесена на узел входа, а Slurm
используется только для запуска уже собранных программ. Успешную линковку и
совместимость библиотек вычислительного узла ещё требуется подтвердить пробой.

## Подготовка и загрузка

На Windows из корня репозитория с локальным Python/NumPy:

```powershell
..\.lab-tools\python\python.exe lab3/prepare_slurm.py
```

Загрузите содержимое `build/deploy-slurm/lab3-upload` через WinSCP в
`/home/2025-00231/lab3-upload/`, подтверждая замену файлов. Внутри должны быть
`common`, `lab3`, `inputs`, `manifest.json`. Не создавайте вложенную папку
`lab3-upload/lab3-upload`. Архив этой же папки: `build/lab3-slurm-upload.zip`.

## Пробное задание

В консоли WinSCP одной строкой:

```bash
bash -lc 'cd /home/2025-00231/lab3-upload && bash lab3/submit_slurm.sh smoke'
```

Скрипт загрузит модули, соберёт обе программы в отдельной папке
`build/korolev.XXXXXXXX`, сохранит журнал, окружение сборки и SHA256 исходников
и исполняемых файлов. Только после успешной сборки появятся `BUILD_OK` и
`Submitted batch job JOB_ID`. При ошибке сборки задание не отправляется.
Уникальная папка сохраняет сборку для ожидающего задания при следующих отправках.
Не удаляйте её до завершения соответствующего задания.

Внутри задания бинарники копируются в каталог результатов; проверяются их хеши
и совпадение исходников со сборкой. Напрямую вызывать `sbatch job.slurm` больше
не нужно: он требует путь к подготовленной сборке от `submit_slurm.sh`.

Просмотр состояния:

```bash
squeue -u "$USER"
```

`PD` — ожидание, `R` — выполнение. Исчезновение из очереди не означает успех.
Откройте `lab3-JOB_ID.out`, `lab3-JOB_ID.err` и
`lab3/results_korolev/JOB_ID-smoke/`. Должен появиться `SUCCESS.txt` с 15
проверенными запусками: N=1,3,17, serial и MPI p=1,2,4,8. Это включает
неравномерное распределение строк и p>N. При ошибке нужны `build.log`, `run.log`
и лог запуска, указанный в исключении. Скрипт останавливается при ошибке.

MPI запускается через Hydra с `I_MPI_HYDRA_BOOTSTRAP=slurm`. Совместимость
с фактической версией Slurm проверяется этой пробой. Локальная проверка Windows
не подтверждает работу планировщика Linux или доступность лицензии Intel.

## Полные замеры — после успешной пробы

```bash
bash -lc 'cd /home/2025-00231/lab3-upload && bash lab3/submit_slurm.sh full'
```

Один узел, 8 слотов по одному ядру, без SMT, память 4 ГБ, лимит 1 час.
Выделенные ресурсы постоянны, меняется число работающих MPI-процессов: 1,2,4,8.
N=200,400,800,1200,1600,2000, по 3 повтора. Всего 18 последовательных и 72
MPI-замера. Оба файла собираются Intel C++ с `-O2 -std=c++14`; имеющийся код
совместим с C++14. Для MPI применяется обёртка `mpiicpc`.

Обмен внутри одного узла: `I_MPI_FABRICS=shm`. Запрошена привязка ранга к ядру
с соблюдением cpuset Slurm. `I_MPI_DEBUG=4` сохраняет назначения рангов в логах:
фактическую привязку нужно проверить перед интерпретацией производительности.
Это масштабирование на одном узле, а не исследование межузлового обмена.

## Проверка без NumPy на сервере

Генератор создаёт входы локально: NumPy default_rng, seed=42+N, целые -10…10.
Независимый эталон C=A@B вычисляется NumPy через float64: каждая промежуточная
целая сумма ограничена 100*N, далеко ниже 2^53, поэтому результат точный.
Для N<=200 эталон дополнительно сверяется с NumPy int64 matmul.

На сервер передаются сжатые A/B, SHA256 всех A/B и эталонных C, версия NumPy.
Python 3.6 со стандартной библиотекой проверяет входы; после каждого запуска
сравнивает SHA256 полного текстового C с эталоном. Нормализуются только CRLF/LF.
Это проверка всех элементов по криптографическому хешу, а не выборка и не только
сравнение serial с MPI. Вероятность коллизии SHA256 пренебрежимо мала; прямое
поэлементное сравнение на сервере не выполняется. Проверка и файловый ввод/вывод
исключены из измеряемого времени. Все 90 строк должны иметь `verified=True`.

## Результаты и отчёт

Скачайте `lab3/results_korolev/JOB_ID-full/` и `lab3-JOB_ID.out/.err`.
Папку временных матриц `work/` скачивать необязательно. Нужны `raw.csv`,
`serial/raw.csv`, `environment.json`, `cluster_environment.txt`, `build.log`,
`build_environment.txt`, `runtime_libraries.txt`, файлы хешей из `build/`,
`run.log`, логи MPI с привязкой и `SUCCESS.txt` (90 измерений).

Графики и таблицы строятся локально с matplotlib:

```powershell
..\.lab-tools\python\python.exe experiments/summarize.py mpi --input lab3/results_korolev/JOB_ID-full --serial-input lab3/results_korolev/JOB_ID-full/serial
```

`speedup_serial=Tserial/Tmpi`, `efficiency_serial=speedup_serial/p`.
Поля `speedup` и `efficiency` отдельно сравнивают MPI с MPI на одном процессе.
В MPI-время входят передача B, распределение A, умножение, сбор C; serial-время
содержит умножение. Файловый ввод/вывод исключён из обоих измерений.

Финальный отчёт пока не готов: нужны реальные кластерные замеры, оборудование,
проверка привязки, таблицы, графики и выводы. Локальные тесты не заменяют кластер.
